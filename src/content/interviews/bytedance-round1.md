### Q1: Loader 和 Plugin 的区别？（16:13）

**候选人回答要点：**

1. **作用范围和阶段不同**
   - Loader：模块编译阶段，针对单个文件的转换处理（如 css-loader、babel-loader）
   - Plugin：介入整个打包生命周期，从编译开始到输出结束，做全局性工作

2. **实现方式不同**
   - Loader：本质是函数，接收源文件内容，返回处理后内容
   - Plugin：基于 Tapable 钩子机制，是带有 `apply` 方法的类

3. **使用方式不同**
   - Loader：在 `module.rules` 数组中配置，指定 test 匹配文件类型
   - Plugin：在 `plugins` 数组中实例化后添加，可传入配置参数

4. **执行特点不同**
   - Loader：可链式调用，从右到左、从下到上执行
   - Plugin：按 webpack 生命周期钩子顺序执行

**面试官评价：** "你对这四个概念的理解还是挺准确的"

**改进建议：**

✅ **优点：** 回答结构清晰，从多个维度对比，有项目实例支撑

⚠️ **可改进：**
- 回答过于冗长（约 400 字），可精简到 200 字以内
- 建议先给出核心区别，再按需展开细节
- 避免重复表述相同概念

**更优回答示例：**

```
核心区别是作用范围和时机：

Loader 是文件转换器，在模块加载阶段工作，针对单个文件做格式转换。
本质是函数，可链式调用，比如 babel-loader 转译 ES6+，css-loader 处理 CSS。

Plugin 是功能扩展器，基于 Tapable 钩子机制，能介入打包全生命周期。
本质是带 apply 方法的类，可做全局操作，比如 HtmlWebpackPlugin 生成 HTML，
MiniCssExtractPlugin 抽离 CSS 文件。

配置上，Loader 在 module.rules 里按文件类型匹配，Plugin 在 plugins 数组里实例化。
```

### Q2: Vite 和 Webpack 在开发环境的区别？（16:14）

**候选人回答要点：**

1. **启动速度**
   - Webpack：从入口递归打包所有模块后才启动服务
   - Vite：基于原生 ES Module，按需编译，启动即快

2. **依赖处理**
   - Webpack：每次重新打包所有依赖
   - Vite：用 esbuild 预构建依赖并缓存，只在版本变更时重建

3. **热更新（HMR）**
   - Webpack：重编译整条依赖链，项目大时慢
   - Vite：精准到单组件，状态可保留

4. **项目实践**
   - MDM 物流平台从 Webpack（启动约 4 分钟）迁移到 Vite（3 秒）

**面试官评价：** "你讲的非常清楚，Vite 的按需加载确实是速度快的关键"

**改进建议：**

✅ **优点：** 有量化数据支撑，对比维度全面

⚠️ **可改进：**
- 可补充生产环境的差异（Vite 生产用 Rollup，Webpack 用自身）
- 提及 Vite 的局限性（如对 CommonJS 支持不完善）

**更优回答示例：**

```
开发环境三大区别：

1. 启动方式：Webpack 需要从入口递归打包所有模块才能启动，Vite 基于原生 ESM，
   启动即快，按需编译。我们项目从 Webpack 4 分钟启动优化到 Vite 3 秒。

2. 依赖处理：Webpack 每次都重新打包依赖，Vite 用 esbuild 预构建并缓存，
   只在 package.json 变更时重建。

3. HMR 热更新：Webpack 重编译整条依赖链，Vite 精准到单模块，状态可保留。

不过 Vite 对 CommonJS 支持不完善，老项目迁移需要处理兼容性问题。
生产环境 Vite 用 Rollup 打包，Webpack 用自身，产物结构也有差异。
```

### Q3: CommonJS 和 ES Module 的区别？（16:16）

**候选人回答要点：**

1. **加载时机**
   - CommonJS：运行时同步加载
   - ES Module：编译时静态分析，异步加载

2. **导出本质**
   - CommonJS：值的拷贝，可修改
   - ES Module：值的引用，只读

3. **Tree Shaking**
   - CommonJS：动态加载无法静态分析，不支持
   - ES Module：静态语法，编译期可确定依赖，支持

4. **动态导入**
   - CommonJS：原生支持 `require('${path}')`
   - ES Module：用 `import()` 函数异步动态导入

**面试官评价：** "你对两种模块规范的区别和 tree shaking 原理的理解都非常到位"

**改进建议：**

✅ **优点：** 对比维度准确，理解深入

⚠️ **可改进：**
- 可补充实际场景：什么时候必须用 CommonJS（如 Node.js 配置文件）
- 提及浏览器原生支持情况

**更优回答示例：**

```
四个核心区别：

1. 加载时机：CommonJS 运行时同步，ES Module 编译时静态分析
2. 导出机制：CommonJS 是值拷贝可修改，ESM 是值引用只读
3. Tree Shaking：ESM 静态语法支持，CommonJS 动态特性不支持
4. 动态导入：CommonJS 原生支持 require(变量)，ESM 需要 import() 函数

实际应用中，现代前端项目优先用 ESM 以支持 Tree Shaking 和按需加载，
但 Node.js 配置文件（如 webpack.config.js）仍常用 CommonJS。
浏览器已原生支持 <script type="module">，这也是 Vite 快速启动的基础。
```

### Q8: Flex 布局（时间未单独记录）

**面试官意图：** 先考察常规 Flex（分栏、主轴/交叉轴、对齐、伸缩），再追问一个**不太常见但很实用**的点：如何在**不破坏整体 flex 排布**的前提下，让**某一个子元素**单独靠左/靠右/居中。

**候选人回答要点：**

1. **常规部分（常见分栏与对齐）**
   - 容器 `display: flex` 后，子项沿**主轴**排列；`flex-direction` 决定主轴方向（默认 `row`，竖向分栏用 `column`）。
   - 与主轴垂直的是**交叉轴**。
   - **主轴**：`justify-content` 分配主轴剩余空间（`flex-start` / `center` / `space-between` 等）。
   - **交叉轴**：`align-items`（单行内）、`align-content`（多行换行时行与行之间）、`align-self`（单个子项覆盖容器对齐）。
   - **子项尺寸**：`flex-grow` / `flex-shrink` / `flex-basis`，`flex` 简写需结合场景理解。

2. **追问：Flex 里有什么「奇怪」/冷门但好用的点？——单独子元素对齐**
   - 场景：例如一行里左侧 logo、中间标题、右侧用户区；或希望**只有一个**子项贴右，其余仍按 `flex-start` 排。
   - **解答要点：** 在 Flex 布局中，给**目标子项**设置 **`margin-left: auto`** 或 **`margin-right: auto`**（或交叉轴方向上的 `margin-top` / `margin-bottom`），可让该 margin **吸收主轴（或交叉轴）上的剩余空间**，从而把该子项「顶」到一侧或居中，而不必为这一个元素再套一层 flex 或绝对定位。
   - 典型：`margin-left: auto` 把当前项推到主轴末端（例如在 `flex-direction: row` 时推到右侧）。

3. **常见坑（补充）**
   - Flex 子项默认 `min-width: auto`，嵌套 flex + 长文本时可能**不收缩溢出**，可用 `min-width: 0` 或配合 `overflow` 处理。

**改进建议：**

✅ 常规部分先一句话：**主轴用 justify，交叉轴用 align；子项单独对齐用 align-self 或 margin auto。**

✅ 追问 `margin: auto` 时，可补一句规范依据：在 Flex 布局中，**自动 margin 会参与剩余空间分配**，因此能精确控制「哪一个」子项吃掉剩余空间。

⚠️ 若再追问「和 `justify-content: space-between` 区别」：`space-between` 是**整组**分布；**margin auto** 是**单个**子项参与分配，两者可组合使用。

### Q9: 遇到的「奇怪」问题，怎么解决的？（时间未单独记录）

## 三、面试建议

### 回答技巧

1. **STAR 法则**
   - Situation：背景（项目规模、技术栈）
   - Task：任务（遇到什么问题）
   - Action：行动（采取什么方案）
   - Result：结果（量化成果）

2. **金字塔原理**
   - 先说结论，再说理由
   - 先说核心，再说细节
   - 先说重要，再说次要

3. **时间控制**
   - 简单问题：30 秒 - 1 分钟
   - 复杂问题：2 - 3 分钟
   - 项目经验：3 - 5 分钟

### 准备清单

1. **技术原理**
   - Webpack/Vite 打包原理
   - Vue 响应式原理
   - 浏览器渲染流程
   - HTTP 缓存策略

2. **项目亮点**
   - 3 个核心项目，每个准备 3 个亮点
   - 每个亮点准备量化数据
   - 准备遇到的难点和解决方案

3. **常见问题**
   - 自我介绍（1 分钟版本）
   - 离职原因
   - 职业规划
   - 为什么选择我们公司

4. **反问问题**
   - 团队技术栈和架构
   - 项目挑战和发展空间
   - 团队规模和协作方式
   - 技术氛围和成长机会

### 模拟练习

   - 录下自己的回答

## 四、具体改进建议

### 1. 精简回答示例

**原回答（约 400 字）：**
> 嗯，好的，我从几个层面来聊聊它们的区别哈：首先是作用范围和阶段不一样，这个是最核心的区别。loader呢，它是"翻译官"的角色，只能在webpack打包的模块编译阶段工作，而且是针对单个文件的...（后续省略）

**优化后（约 150 字）：**
> 核心区别是作用范围和时机：Loader 是文件转换器，在模块加载阶段针对单个文件做格式转换，本质是函数，可链式调用。Plugin 是功能扩展器，基于 Tapable 钩子机制，能介入打包全生命周期，本质是带 apply 方法的类。配置上，Loader 在 module.rules 里按文件类型匹配，Plugin 在 plugins 数组里实例化。

### 2. 增加反问环节

**建议在面试中适时反问：**

- "我们团队目前的微前端方案是什么？我之前用的是 Module Federation，不知道是否有机会分享经验？"
- "刚才提到的虚拟列表优化，我们项目是万级数据，不知道贵司的数据量级是多少？"
- "关于 AI 工具的使用，我们团队目前的态度是什么？是鼓励使用还是有所限制？"

### 3. 补充量化数据

**原表述：**
> "性能有明显提升"

**优化后：**
> "首屏加载时间从 3.2s 降至 1.1s，LCP 从 4.5s 降至 1.8s，Lighthouse 性能评分从 65 提升到 92"

### 4. 结构化表达

**使用"三点式"回答：**

```
这个问题我从三个方面来说：

第一，技术选型上...
第二，实现方案上...
第三，优化效果上...

总结一下就是...
```
